# Write-site audit and parts-model check (2026-10-16)

STATUS: JOURNAL. Premise record for LW-393 (per-part arming and the startup report). Read with
docs/LIVE_LEDGER.md as the tie-breaker for any runtime claim. Nothing here is a ledger PROVEN flip.

## Why this exists

The September 2026 game update removed the copy protection and recompiled the game with nothing
moved. The mod's startup guard gated on the game's build stamp, read a different stamp, and kept
the whole mod off for a month (LW-387, LW-388). The owner ruled on 2026-10-16 that a mod which
breaks in parts beats a tower that falls at once: each part of the mod should check the memory it
depends on, switch off alone when that check fails, and the startup report should list every part
as ON or OFF with the reason. Before designing that, two questions needed real answers: where does
the mod write into the game, and what does each player-visible part depend on.

## Method

Ten independent read-only passes: four auditors over fixed slices of the 59 files that write
game memory (every W8/W16/WriteBytes/MemBits/TryWrite call traced to its address source and the
check that stands in front of it), four skeptics re-reading the same code to refute the auditors'
region, check and save-exposure calls, one reader documenting how writes are gated today, and one
completeness critic hunting for write paths outside the Mem seam. Then one more skeptic took the
six-part dependency model drawn from the audit as its defendant.

## Headline numbers

129 write sites (127 found by the auditors, 2 by the skeptics) in 59 files, hitting nine kinds of
memory. Skeptic corrections: 16, none of which changed a region or a save verdict.

## The parts-model check: what the first model got wrong

The coordinator's first model had six parts (kill counting and growth, card paint, battle
signatures, weapon commands, banners, extended inventory) with three already gated. The skeptic
refuted or corrected it in these places, each with file and line evidence in the session record:

1. The game build key (TimeDateStamp plus SizeOfImage) is the real global switch, and it is wired
   into more than the main guard: the extended inventory refuses at boot on the same two constants
   (ExtendedInventory.cs 106 to 112, fed from Engine.cs 275), the prompt hook arms only on the main
   guard's Armed edge (Engine.cs 509, LaunchGuard.cs 126 to 145), and the kit lane steps only while
   the main guard is Armed (LaunchGuard.KitLane.cs 26 to 31). With today's code any patch turns
   everything off, the three "independent" parts included. Demoting the build key to a report line
   is step one of the design.
2. The band and the combat structs are one pinned region. CombatAnchor is a fixed image pin and
   BandReadBase and FrameReadBase are measured from it (Offsets.cs 199 to 207, 361); GrowthEngine's
   locate is a bounded walk of plus or minus 24 slots around that pin, not a heap search
   (GrowthEngine.Locate.cs 35 to 43). The region the first model never named is the static unit
   array at 0x140899F50 (Offsets.cs 89 to 95), read by the kill oracle (EnemyOracle.cs, the
   identity every kill credit must pass at KillTracker.cs 150), by Band.cs 137 to 162 for several
   signature fingerprints, and by Plague.
3. A shared sensing layer sits under every part: Slot0, Slot9, BattleMode, PauseFlag, EventId and
   SubmenuFlag are read every tick (Engine.cs 585 to 593, 638) and BattleState derives everything
   from them; ActorPtr, TurnQueue and the Acted global feed attribution, Iai, ProvokeHold,
   FeignDeath, Puppeteer and the card. One consumer is harmful on a bad read: PlaythroughReset
   archives and clears kills.json after thirty ticks of EventId 2 with BattleMode 0 out of live
   (PlaythroughReset.Policy.cs 28, PlaythroughReset.cs 53). This became LW-395.
4. The harmful-write class is specific and small: Bulwark's terrain grid (process-wide, once
   crashed the game when stale), the weapon palette banks (30-byte block writes), the poach den
   store (save state, no undo), Provoke's action and inflict tables (captured, never compared to
   vanilla, so a moved table takes seven authored bytes), the WP table hold (owned-byte check,
   residual risk), WpScratchPainter's static scratch byte, and GunSlinger's roster off-hand and
   support stamps (save state; GunSlinger is not an ISignature and ticks on the Always gate in and
   out of battle). Everything else fails closed: kill credit needs a band corpse and an oracle
   identity from the separate static array to agree, growth needs a fingerprint match, band
   signatures write only to an entry that passed Band.IsValid plus a wielder fingerprint.
5. The kit lane does not gate every write the three commands make: it verifies records 8 and 9
   of the JobCommand table only; the roster learned bits (Barrage.cs 247, ShadowBlade.cs 199,
   Provoke.cs 194) stand behind the main guard's Ramza row alone, and Provoke.Table writes two
   other tables. The JobCommand slot write itself is fail-closed (Barrage.Policy.cs 170 to 185).
6. The parts list missed GunSlinger's twin grant, PlaythroughReset, the Reliquary legend store,
   IconGlow (file I/O only), WpTableHold, WeaponPalette and LivingPoach, each on its own tick row.
7. The tick table has per-row gates and TickGates.KitLane proves the lane shape works
   (TickPhase.cs 31 to 37, Engine.cs 352 to 360), but field-signatures is one row ticking 19
   modules (Engine.cs 412 to 417) and ResetBattleState resets every module unconditionally
   (Engine.cs 542 to 565), so per-part gating needs a per-module gate inside the loop or a split.

## How writes are gated today (the guard reader's findings)

1. ICodePatcher.TryWrite has no gate at all (CodePatcher.cs 61 to 79) and some callers run on the
   game's thread inside detours the instant the game calls them; their only gate is
   ExtendedInventory.Armed, decided at boot. The runtime is born disarmed for the Mem path only.
2. Mem.WritesEnabled defaults TRUE (Mem.cs 33); only Mod.StartEngine flips it false. Any other
   construction path runs writes-on from the first tick.
3. The gate sits below the IGameMemory seam, so no unit test can observe a subsystem writing while
   disarmed; every fake records writes regardless. A per-door model built as a seam decorator would
   make the gate testable for the first time.
4. MemBits reaches Mem through its own private LiveMemory (MemBits.cs 17), not the injected one;
   a per-instance door would miss every MemBits caller unless they switch to the seam overloads.
5. Unreadable is a silent forever retry with no log, counter or scout (FingerprintGuard.cs 125 to
   129); LaunchGuardTests.cs 113 to 130 pins it as correct. The ASLR incident is this behavior.
6. Armed is terminal (FingerprintGuard.cs 67 to 69, 93). Closing a door mid-session needs a new
   state in the core.
7. The kit lane protects its region by tick exclusion, not by gating the write.
8. The roster probe cannot tell an unreadable page from an empty slot (Landmarks.cs 70 to 71 via
   the fail-safe U8 read of 0), so a roster move after a save loads reads as Unreadable, not
   Mismatch, and retries silently.
9. StandDownNotice raises one MessageBoxW per guard instance; N doors means up to N boxes unless
   aggregated.

### Guard model (today)

**writesEnabledGates:** Plain version: there is exactly one on/off switch for ordinary game-memory writes, and it lives inside three tiny functions in one file. Everything that writes through the normal path hits one of those three; everything else has its own door or no door at all.

Tech:
- The switch: `Mem.WritesEnabled` (LivingWeapon/Memory/Mem.cs:33), `internal static volatile bool`, DEFAULT TRUE (so tests run writes-on; only production flips it false in Mod.StartEngine, Mod.cs:129).
- The three primitives that honor it: `Mem.WriteBytes` (Mem.cs:64-68, `if (!WritesEnabled) return;` at :66), `Mem.W8` (Mem.cs:70-76, gate at :72), `Mem.W16` (Mem.cs:78-85, gate at :80). Nothing else in Mem writes. Reads (ReadBytes/TryReadBytes/ReadInto/U8/U16/U32/U64, Mem.cs:39-109) are never gated.
- Funnels INTO those three: `LiveMemory.WriteBytes/W8/W16` (Memory/GameMemory.cs:60-62) delegate 1:1 to Mem, so every subsystem that takes `IGameMemory` and is handed Engine's one `LiveMemory` (Engine.cs:146) is gated. `MemBits.OrSet/Clear` (Memory/MemBits.cs:24,29) go through a PRIVATE STATIC `LiveMemory _live` (MemBits.cs:17) into `mem.W8` (MemBits.cs:43,56), so they are gated too, but through their own hidden instance, not the Engine-injected one. Direct static `Mem.W16/WriteBytes` calls exist only in Dev/NumeralSpike.cs:283,292,313,315 (LWDEV only).
- Write paths that BYPASS Mem.WritesEnabled entirely:
  1. `ICodePatcher.TryWrite` / `LiveCodePatcher.TryWrite` (Memory/CodePatcher.cs:36, 61-79): VirtualProtect + WriteProcessMemory with NO gate of any kind (not WritesEnabled, not LaunchGuard, not ExtendedInventory.Armed). The class doc says so explicitly (CodePatcher.cs:9-17): it is gated "differently" by caller discipline only. ~60 call sites, all under LivingWeapon/Extended/ and Persistence/BagReplay.cs, Persistence/TemplateSeat.cs (grep `TryWrite(`). These include writes that run on the GAME's thread inside Reloaded detours, independent of the Engine tick and of LaunchGuard: `ExtendedInventory.ReplayOnLoad` (Extended/ExtendedInventory.Tick.cs:96-106, called from SaveEdgeHooks.AfterApply), OrderRebuildHook.cs:148 and OrderRebuildHook.Seat.cs:75, ListBuilderHook.Pool.cs:52-92, InventoryResetHook.cs:130. Their only gate is `ExtendedInventory.Armed` (ExtendedInventory.Tick.cs:98) plus each site's own old-byte verify.
  2. `LiveRegionWalker.Commit` / VirtualAlloc (Memory/NearAllocator.cs:140-141): allocates new RWX pages; not a write into game memory but ungated.
  3. Reloaded.Hooks detour installs (`hooks.CreateHook<...>(...).Activate()`): PromptSwapHook.cs:120 (deferred until main guard Armed via OfferHookArm, Engine.cs:510, AND prologue-verified via HookLandmark), CategoryGetterHook.cs:71, OrderRebuildHook.cs:105, InventoryResetHook.cs:99, ListBuilderHook.cs:142, SaveEdgeHooks.cs:121-123 (the five Extended detours: installed at BootArm BEFORE the guard has decided anything, each prologue-verified via HookLandmark.Verify, Guard/HookLandmark.cs:21-27).
  4. PromptSwapHook.WritePinned (PromptSwapHook.cs:167-173) writes only into the mod's own pinned buffer, not game memory; listed for completeness.
- Engine-side gating ABOVE Mem: `Engine.Tick` returns before any phase runs until `_launchGuard.Armed` (Engine.cs:576-581), so even the ungated patcher writes that live on TickPhase rows ("extended-caps/bag/shops", Engine.cs:397-404, TickGates.Always) do not run pre-arm. The detour-thread patcher writes above are the ones that truly ignore the guard.

**codePatcherHonorsGate:** No. Plain version: the code-patch tool has no safety switch of its own; it trusts whoever holds it.

Tech: `LiveCodePatcher.TryWrite` (Memory/CodePatcher.cs:61-79) checks only `bytes != null && bytes.Length > 0 && address > 0`, then VirtualProtect(PAGE_EXECUTE_READWRITE) + WriteProcessMemory + restore protection. It never reads `Mem.WritesEnabled`, never consults LaunchGuard, never consults `ExtendedInventory.Armed`. The doc (CodePatcher.cs:9-17) states the reason: the boot patches must land before the game executes an instruction, long before Ramza's roster row is readable, so they cannot ride the LaunchGuard edge. The substitute gate is entirely in the callers: `ExtendedInventory.BootArm` checks the PE build-key landmark first (ExtendedInventory.cs:106-113, probe built in Engine.cs:276-277 from the same `LaunchGuard.ExpectedTimeDateStamp/ExpectedSizeOfImage`), then `BytePatchSet.Apply` verifies EVERY site's old byte before writing ANY (Extended/BytePatchSet.cs:27-33) and rolls back in reverse on a refused write (:36-41, :48-53); `AccessorEntryHook.Install` verifies the full expected entry bytes before stealing them (Extended/AccessorEntryHook.cs:58-61); `PendingPatch.Step` refuses a Foreign byte for the session (BytePatchSet.cs:82-83); and the whole arm is one transaction with `RollBack()` on first refusal (ExtendedInventory.cs:115-116, Hooks.cs:57-73). Post-arm patcher writes (SeedBag Arm.cs:81, BagReplay.Apply, TemplateSeat.Apply, ShopFlagsMirror.Sync, the detour-thread writes) are gated only on `ExtendedInventory.Armed` (ExtendedInventory.Tick.cs:57,82,98,114), which is set once at ExtendedInventory.cs:117 and never cleared. So the Extended family is ALREADY a fully independent per-door arm with its own landmark (PE key), its own per-site checks, its own refusal notice (Refuse, ExtendedInventory.cs:141-145, WARN tier, no message box) and its own Armed flag. It is the closest existing model of what the owner is asking for, and it is also the one family whose writes can land while LaunchGuard is still Verifying.

**mainLaneLandmarks:** Plain version: the main guard asks two questions every 33 ms until it gets a clear yes or a clear no: "is this the exact game build I was built for?" and "does Ramza's save-file row look like Ramza?". A yes to both turns writes on for good. Thirty straight no's in a row turns the whole mod off for good. "Can't tell yet" just asks again.

Tech:
- Construction: `LaunchGuard` ctor (Guard/LaunchGuard.cs:73-99) builds TWO `FingerprintGuard` instances. Main guard landmarks array (LaunchGuard.cs:89-93):
  1. `FingerprintGuard.PeBuildKey(tryRead, ImageBase.Base, expectedTimeDateStamp, ExpectedSizeOfImage)` (factory at Guard/FingerprintGuard.cs:155-172). Reads e_lfanew u32 at base+0x3C, TimeDateStamp at base+e_lfanew+8, SizeOfImage at base+e_lfanew+0x50 (constants :147-149). Any failed/short read -> Unreadable (:160-165); both equal -> Match; else Mismatch with a detail string naming expected and observed (:168-170). Expected constants: `ExpectedTimeDateStamp = 0x6A5E4A1B`, `ExpectedSizeOfImage = 0x03F9E000` (Guard/LaunchGuard.Landmarks.cs:32-33, the Denuvo-free 1.5.2, buildid 24304444). The dev drill XORs the expected stamp with 1 (LaunchGuard.cs:87) so the landmark reads Mismatch against healthy memory. Address derivation: `ImageBase.Base` (Memory/ImageBase.cs:22), resolved once in Mod.StartEngine (Mod.cs:77-80) via GetModuleHandleW(null) (ImageBase.cs:46-68); if resolution fails, Base stays the preferred 0x140000000 and the landmark reads Unreadable forever (pinned by LaunchGuardTests.cs:113-130).
  2. `FingerprintGuard.Custom("ramza-roster-row", ProbeRamzaRosterRow)` (LaunchGuard.cs:91; probe at Landmarks.cs:67-85). Reads `Offsets.RosterBase + RLevel` via `_mem.U8`; level outside 1..99 -> Unreadable ("unpopulated slot (title screen)", :71). Otherwise reads RNameId (U16), RSprite, RBrave, RFaith; Match iff nameId==1 && sprite<0x80 && brave<=100 && faith<=100 (:78-80), else Mismatch with observed fields (:82-84). Note this probe goes through `IGameMemory.U8/U16` (which return 0 on a failed read, Mem.cs:95-96), so an unreadable roster page is indistinguishable from an empty slot: both read level 0 -> Unreadable. Address derivation: `Offsets.RosterBase` (an `ImageBase.At(0x14...)` pin) plus R* field offsets; this is SAVE STATE memory.
- Verdict semantics (FingerprintGuard.Step, FingerprintGuard.cs:91-138): every Step probes EVERY landmark fresh, no per-landmark latching. All Match -> State=Armed, `_onArmed` fires once (:117-123). Any Mismatch -> `_mismatchStreak++`; at `>= mismatchDebounce` -> State=StoodDown, `_onStandDown(joined details)` once (:131-137). A Step with zero Mismatches but some Unreadable -> streak reset to 0, stay Verifying (:125-129). Both terminal states stop probing forever (:93). `MismatchDebounce = 30` (Landmarks.cs:65) = ~990 ms at the 33 ms tick. Verify-once is load-bearing: Barrage later edits the JobCommand region legitimately (LaunchGuard.cs:33-35; FingerprintGuard.cs:67-69).
- Driver: `Engine.Tick` (Engine.cs:576-581): while `!_launchGuard.Armed`, call `_launchGuard.Step()`, and if StoodDown also `_anchorScout.Tick()`, then `return` (nothing else in the engine runs). Once Armed, Step is never called again; the check is one bool read.
- Armed edge (`LaunchGuard.ArmedEdge`, LaunchGuard.cs:129-142): sets `Mem.WritesEnabled = true` (:130), records "guard"/"armed..." into the flight ring (:133), logs the ARMED_MARK line "Living Weapons is armed" (:134-135, pinned by LaunchGuardTests.cs:836-865 because tools/scan_logs.py keys on it), then fires any stashed `_pendingHookArm` exactly once under `_hookLock` (:136-141). `OfferHookArm` (LaunchGuard.cs:120-127) arms immediately if already Armed, stashes if Verifying, and silently drops if StoodDown (pinned LaunchGuardTests.cs:295-307). Production uses it for the PromptSwapHook detour (Engine.cs:510).
- Thread contract: FingerprintGuard is single-thread by contract (FingerprintGuard.cs:12-15); the cross-thread visibility of the verdict is the adapter's job, done via the `volatile` WritesEnabled (Mem.cs:30-32).
- Tests: LaunchGuardTests.cs (RamzaRow_* :133-176, ForceMismatch :216-224, Armed_edge_enables_mem_writes :227-242, StoodDown_never_enables_writes :245-260, hook-arm handshake :263-307, notice/flight/flush :310-419, relocation :98-130); FingerprintGuardTests.cs covers the core state machine (:33-210); MemGuardTests.cs pins the three primitives honoring the flag (:15-59).

**kitLane:** Plain version: there is already a second, smaller guard that watches one shared table and, if another mod has rewritten it, switches off only the three weapon-granted commands while everything else keeps running. It is the one existing proof that "turn off just this part" can be done here, and it shows exactly which seams had to be touched.

**standDownPath:** Plain version: when the main guard gives up, the mod goes quiet for the rest of the session, says so once in the log and once in a Windows pop-up, saves a black-box recording of why, and then spends its idle ticks hunting for where the moved landmarks went so the next re-anchor starts with a map. Nothing is "restored" because nothing was ever written: the switch simply never turns on.

Tech:
- Trigger: `FingerprintGuard.Step` sets `State = StoodDown` and calls `_onStandDown(diag)` exactly once (FingerprintGuard.cs:131-137); for the main guard that is `LaunchGuard.StandDown` (LaunchGuard.cs:144-191).

**subsystemArmHooks:** Plain version: no. The signature modules have no "on/off" lever of their own; the engine decides whether to call them. **unreadableHandling:** Plain version: if the guard cannot read a landmark it assumes "not yet" and quietly tries again forever, without ever saying anything. That is the right call at the title screen (Ramza's row is empty until a save loads) and exactly the wrong call when the game has moved out from under the mod, which is how the Denuvo-free ASLR build produced a mod that simply never switched on and never said why.

Tech:
- Core rule (FingerprintGuard.Step, FingerprintGuard.cs:101-103, 125-129): an Unreadable verdict sets `anyUnreadable`, and a Step with no Mismatch resets `_mismatchStreak = 0` and returns with State still Verifying. There is no Unreadable counter, no timeout, no log line, no flight record, no notice. Both the Match/Unreadable mix and the all-Unreadable case behave identically (pinned FingerprintGuardTests.cs:74-101).
- Producers of Unreadable on the main lane: PeBuildKey on any failed u32 read (FingerprintGuard.cs:160-165); ProbeRamzaRosterRow on level outside 1..99 (Landmarks.cs:71), which covers BOTH "no save loaded" and "page unreadable / address wrong" because `IGameMemory.U8` fails safe to 0 (Mem.cs:95). ByteSignature (unused by LaunchGuard today, FingerprintGuard.cs:180-197) also treats an ALL-ZERO window as Unreadable (:186-189), the documented boot-window escape.
- Engine behaviour while Verifying: `Engine.Tick` early-returns every tick (Engine.cs:576-581), the AnchorScout does NOT tick (only on StoodDown, :580), nothing is logged after the launch header. From the outside the session looks like a healthy pre-save wait, forever.
- The ASLR silence case is exactly this: the Denuvo-free build loads at a random base; with `ImageBase.Base` left at the preferred 0x140000000, every landmark read fails -> Unreadable -> silent retry forever. Pinned as the player symptom by LaunchGuardTests.Guard_stays_unreadable_when_the_image_is_relocated_but_the_base_is_not_resolved (LaunchGuardTests.cs:113-130: 100 Steps, still Verifying) and documented in docs/PATCH_REANCHOR.md "Standing facts" ("the guard's PE landmark reads UNREADABLE, not Mismatch, so there is NO loud line and NO box; the mod simply never arms"). The LW-387 fix did not change the guard's Unreadable semantics; it fixed the address (Mod.cs:77-80 resolves the base once, and logs a WARN "If the game loaded elsewhere the startup guard will never arm" only when GetModuleHandleW itself fails).
- Kit lane: `ProbeKitLaneTable` returns Unreadable only on a failed/short TryReadBytes (KitLane.cs:38) and deliberately NOT on all-zero (:48-56), because post-arm the table is file-baked image data, so a zero window means another mod blanked it. A lane read failure therefore also retries silently forever (pinned LaunchGuardTests.cs:179-206).
- Consequence for a per-door model: any new per-region landmark that is only readable in some game state (a band-array door readable only in battle, a turn-queue door readable only mid-turn) inherits this "silent forever" behaviour by default; a per-door design needs either a per-door Unreadable timeout that at least LOGS (not stands down), or a per-door scout, or it reproduces the LW-387 failure mode once per door.

**plumbingEstimate:** Plain version: the guard core itself needs no changes, and the kit lane already proves the shape. The real work is in three places: writing a trustworthy "is this region still where I think it is" probe for each region (the hard, per-region research part), teaching the engine's tick table and the signature list to skip only the modules behind a closed door, and deciding whether the write primitive itself should know about doors. Honest size: a medium arc, not a weekend, and most of it is probe research, not plumbing.

**surprises:** 1. `ICodePatcher.TryWrite` has no gate at all (CodePatcher.cs:61-79), and some of its callers run on the GAME's thread inside detours (ReplayOnLoad via SaveEdgeHooks, OrderRebuildHook.Seat.cs:75, ListBuilderHook.Pool.cs:52-92, InventoryResetHook.cs:130) the instant the game calls them, independent of LaunchGuard's state. Their only gate is `ExtendedInventory.Armed`. So "the runtime is born disarmed and nothing writes until LaunchGuard arms" (the project notes' wording) is true for the Mem path only; the Extended family writes game memory and installs five detours before the main guard has decided anything, by design (ExtendedInventory.cs:9-15, Engine.cs:499-505). It is already an independent door, which is both the strongest argument that per-door works and the place where a per-door audit should start.
2. `Mem.WritesEnabled` defaults TRUE (Mem.cs:33). Only Mod.StartEngine flips it false (Mod.cs:129). Any other construction path for Engine (tests, a future second entry point) runs writes-on from the first tick. The born-disarmed property is a Mod.cs convention, not a Mem invariant.
3. The gate sits BELOW the IGameMemory seam, so no unit test can observe "subsystem X wrote while disarmed": every fake (FakeSparseMemory.cs:137-148, FakeHeap.cs:117-126, etc.) records writes regardless. MemGuardTests only proves the three primitives honor the flag against a pinned buffer. A per-door model built as an IGameMemory decorator would make the gate testable for the first time.
4. `MemBits` reaches Mem through its OWN private static `LiveMemory` (MemBits.cs:17), not the Engine-injected instance. Harmless today (both end in static Mem) but any per-instance door would silently miss every MemBits.OrSet/Clear caller unless they are switched to the IGameMemory overloads.
5. Unreadable is a silent forever-retry with no log, no counter, no scout (FingerprintGuard.cs:125-129; AnchorScout only on StoodDown, Engine.cs:580). The ASLR incident (LW-387) is this behaviour, and LaunchGuardTests.cs:113-130 PINS it as correct. A per-door model multiplies the number of landmarks that can be Unreadable and so multiplies this failure mode unless each door gets at least a "still waiting after N seconds" log line.
6. Armed is terminal and nothing ever re-verifies or re-disarms (FingerprintGuard.cs:67-69, 93). There is no runtime path that sets `Mem.WritesEnabled = false` after the Armed edge. A per-door model that wanted to CLOSE a door mid-session (e.g. a hidden-writer tripwire like ListRelocation.CheckOldBlocks, ExtendedInventory.Tick.cs:118) would need a new state in the core.
7. The kit lane protects its region by TICK EXCLUSION, not by gating the write: Barrage.cs:247 `_mem.W8` would land if called while the lane is down; the three modules are simply never ticked (Engine.cs:237, 353-361). Fine today because they are the only callers; a per-door design must choose between this shape and a primitive-level gate explicitly.
8. The roster probe cannot distinguish "unreadable page" from "empty slot" (Landmarks.cs:70-71 via `U8` fail-safe 0, Mem.cs:95), so a roster-region move after a save loads reads as Unreadable (level 0) rather than Mismatch, and the main guard would retry silently rather than stand down. Only the PE key is reliably early-decidable (LaunchGuard.cs:24-26).
9. One MessageBoxW per guard instance (StandDownNotice.cs:41-57, once per instance by construction). Two instances today means at most two boxes per session; N doors means up to N boxes unless aggregated.
10. The Extended family's PE-key probe and LaunchGuard's share constants (Engine.cs:276-277 uses `LaunchGuard.ExpectedTimeDateStamp/ExpectedSizeOfImage`) but are two separate landmark evaluations with different consequences (Extended: refuse + WARN, no box; main: stand down + Error + box). A game patch today produces TWO distinct refusals in the log for one cause.
11. PromptSwapHook is double-gated (OfferHookArm defers until the main guard arms, Engine.cs:510, AND HookLandmark prologue verify, PromptSwapHook.cs:110-116) while the five Extended detours are prologue-verified only and install pre-guard.
